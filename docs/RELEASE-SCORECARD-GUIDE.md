# Release Scorecard Guide

This guide explains how to read the release scorecard produced by
`scripts/generate-release-scorecard.mjs`. It describes every field the script
emits, where the underlying evidence comes from, how thresholds are applied, and
who owns remediation.

The most important distinction in this guide is between a **failed release gate**
(`BLOCKED`) and **missing optional evidence** (`WARN`). A `WARN` never blocks a
release on its own; a `BLOCKED` status always does.

> All examples in this document are synthetic and illustrative only. They do not
> reflect the state of any real release.

---

## 1. Where the scorecard comes from

The scorecard is generated by `scripts/generate-release-scorecard.mjs`. It
aggregates the results of four check functions:

| Check function | Category name | Primary artifact source |
| --- | --- | --- |
| `checkTests` | `tests` | Test runner output / coverage report |
| `checkSecurity` | `security` | Dependency audit and secret-scanning output |
| `checkBuildAndCaching` | `build-and-caching` | Build log and cache statistics |
| `checkReleaseReadiness` | `release-readiness` | Release metadata, changelog, and gate inputs |

Each category contributes a weighted score. The weighted scores are summed into
`overall.score`, which is then mapped to a `grade` and a `status`.

---

## 2. Top-level fields

### `metadata`

Descriptive information about the scorecard run itself. It is not scored.

| Field | Meaning | Source |
| --- | --- | --- |
| `metadata.generatedAt` | ISO-8601 timestamp of generation | Set by the generator at runtime |
| `metadata.version` | Version of the release being scored | Release metadata read by `checkReleaseReadiness` |
| `metadata.commit` | Commit SHA the scorecard was computed against | CI environment / release metadata |

`metadata` never affects `overall.score`. If it is missing or malformed, treat
the scorecard as untrustworthy and regenerate it.

**Remediation owner:** Release manager (regenerate the scorecard).

---

### `overall.score`

The weighted sum of all category scores, on a 0–100 scale.

- Computed as `sum(categories[].score * categories[].weight)`.
- Weights are expected to sum to `1.0`; if they do not, the score is not
  comparable across runs and should be treated as invalid.

**Threshold semantics:** `overall.score` is only a number. The pass/fail
interpretation lives in `overall.grade` and `overall.status` (below).

**Remediation owner:** Determined by the lowest-scoring category (see
Section 3).

---

### `overall.grade`

A letter grade derived from `overall.score` using these thresholds:

| `overall.score` | `overall.grade` |
| --- | --- |
| `>= 95` | `A+` |
| `>= 85` | `A` |
| `>= 75` | `B` |
| `>= 60` | `C` |
| `< 60` | `F` |

Grades are informational. They summarize quality but do not by themselves block
a release — `overall.status` does.

**Remediation owner:** Determined by the lowest-scoring category.

---

### `overall.status`

The release gate verdict. Two values are possible:

| `overall.status` | Meaning | Blocks release? |
| --- | --- | --- |
| `PASS` | All required gates satisfied | No |
| `BLOCKED` | At least one required gate failed | **Yes** |

**Threshold semantics:** `overall.status` is `BLOCKED` when `overall.grade` is
`F` (i.e. `overall.score < 60`) **or** when any category reports a hard failure
(see `categories[].status`). Otherwise it is `PASS`.

> **Key distinction:** `BLOCKED` means a required gate failed and the release
> must not proceed. A `WARN` (see below) means optional evidence is missing and
> the release may proceed, but the gap should be closed.

**Remediation owner:** Release manager coordinates; the owner of the failing
category fixes the underlying issue.

---

### `blockers`

An array of human-readable strings describing every condition that forced
`overall.status` to `BLOCKED`. When `overall.status` is `PASS`, `blockers` is
empty.

Each blocker entry corresponds to a hard failure surfaced by one of the check
functions. To remediate, map each blocker back to its category and follow the
owner listed in Section 3.

**Remediation owner:** Owner of the category named in the blocker.

---

## 3. Category fields

Each entry in `categories[]` represents one check function's result.

### `categories[].name`

The category identifier. One of:

- `tests` — produced by `checkTests`
- `security` — produced by `checkSecurity`
- `build-and-caching` — produced by `checkBuildAndCaching`
- `release-readiness` — produced by `checkReleaseReadiness`

**Remediation owner:** See the per-category table below.

---

### `categories[].score`

The category's score on a 0–100 scale, computed by its check function from the
category's artifact source.

**Threshold semantics:** A category score `>= 80` yields `PASS`; a score
`< 80` yields `WARN`. A category can additionally be forced to `FAIL` by a hard
failure condition in its check function (for example, a detected secret or a
broken build), regardless of numeric score.

**Artifact sources and owners by category:**

| Category | Artifact source | Remediation owner |
| --- | --- | --- |
| `tests` | Test runner output and coverage report | Engineering team owning the failing tests |
| `security` | Dependency audit and secret-scanning output | Security owner / maintainer on call |
| `build-and-caching` | Build log and cache statistics | Build/infrastructure maintainer |
| `release-readiness` | Release metadata, changelog, gate inputs | Release manager |

---

### `categories[].status`

The category verdict. Three values are possible:

| `categories[].status` | Meaning | Blocks release? |
| --- | --- | --- |
| `PASS` | Score `>= 80` and no hard failure | No |
| `WARN` | Score `< 80` but no hard failure (missing optional evidence) | No |
| `FAIL` | Hard failure detected by the check function | **Yes** (forces `overall.status = BLOCKED`) |

> **Key distinction:** `WARN` is *not* a gate failure. It signals that optional
> evidence is missing or below the quality bar. `FAIL` is a gate failure and
> always blocks the release.

**Remediation owner:** Per the category table above.

---

### `categories[].weight`

The weight applied to this category when computing `overall.score`. Weights are
fixed per category and sum to `1.0`.

**Threshold semantics:** Weights do not have pass/fail thresholds; they only
determine how much a category's score influences `overall.score`. A low score in
a high-weight category moves `overall.score` (and therefore `overall.grade`)
more than the same low score in a low-weight category.

**Remediation owner:** N/A (configuration value).

---

### `categories[].details`

A free-form object produced by the category's check function, containing the
supporting evidence behind the score. The exact keys depend on the category:

- `tests` (`checkTests`): test counts, pass/fail counts, coverage percentage.
- `security` (`checkSecurity`): audit finding counts by severity, secret-scan
  result.
- `build-and-caching` (`checkBuildAndCaching`): build success flag, cache hit
  rate, build duration.
- `release-readiness` (`checkReleaseReadiness`): changelog presence, version
  consistency, required-gate inputs.

`details` is diagnostic. Use it to understand *why* a category scored as it did,
but do not parse it as a stable contract unless documented by the relevant check
function.

**Remediation owner:** Per the category table above.

---

## 4. Reading a scorecard: worked synthetic examples

### Example A — passing release

```json
{
  "metadata": { "generatedAt": "2025-01-01T00:00:00Z", "version": "1.2.3", "commit": "abc1234" },
  "overall": { "score": 91.5, "grade": "A", "status": "PASS" },
  "categories": [
    { "name": "tests", "score": 95, "status": "PASS", "weight": 0.4, "details": {} },
    { "name": "security", "score": 90, "status": "PASS", "weight": 0.3, "details": {} },
    { "name": "build-and-caching", "score": 88, "status": "PASS", "weight": 0.2, "details": {} },
    { "name": "release-readiness", "score": 92, "status": "PASS", "weight": 0.1, "details": {} }
  ],
  "blockers": []
}
```

Interpretation: every category is `PASS`, `overall.score` is `91.5` (grade `A`),
and `overall.status` is `PASS`. The release may proceed.

### Example B — missing optional evidence (WARN, not blocked)

```json
{
  "metadata": { "generatedAt": "2025-01-01T00:00:00Z", "version": "1.2.3", "commit": "abc1234" },
  "overall": { "score": 84.0, "grade": "B", "status": "PASS" },
  "categories": [
    { "name": "tests", "score": 92, "status": "PASS", "weight": 0.4, "details": {} },
    { "name": "security", "score": 90, "status": "PASS", "weight": 0.3, "details": {} },
    { "name": "build-and-caching", "score": 70, "status": "WARN", "weight": 0.2, "details": {} },
    { "name": "release-readiness", "score": 85, "status": "PASS", "weight": 0.1, "details": {} }
  ],
  "blockers": []
}
```

Interpretation: `build-and-caching` scored `70` (`< 80`), so it is `WARN`. This
is **missing optional evidence**, not a failed gate. `overall.status` remains
`PASS` and the release may proceed. The build/infrastructure maintainer should
close the gap (for example, restore cache statistics) before the next release.

### Example C — failed release gate (BLOCKED)

```json
{
  "metadata": { "generatedAt": "2025-01-01T00:00:00Z", "version": "1.2.3", "commit": "abc1234" },
  "overall": { "score": 58.0, "grade": "F", "status": "BLOCKED" },
  "categories": [
    { "name": "tests", "score": 40, "status": "FAIL", "weight": 0.4, "details": {} },
    { "name": "security", "score": 90, "status": "PASS", "weight": 0.3, "details": {} },
    { "name": "build-and-caching", "score": 80, "status": "PASS", "weight": 0.2, "details": {} },
    { "name": "release-readiness", "score": 85, "status": "PASS", "weight": 0.1, "details": {} }
  ],
  "blockers": ["tests: hard failure detected by checkTests"]
}
```

Interpretation: `tests` is `FAIL` (a hard failure), which forces
`overall.status = BLOCKED`, and `overall.score` is `58` (grade `F`). This is a
**failed release gate**: the release must not proceed. The engineering team
owning the failing tests must remediate, then regenerate the scorecard.

---

## 5. Quick reference: WARN vs BLOCKED

| Signal | Field | Blocks release? | Meaning | Owner |
| --- | --- | --- | --- | --- |
| `WARN` | `categories[].status` | No | Optional evidence missing / below bar | Category owner |
| `FAIL` | `categories[].status` | Yes | Hard failure in a required check | Category owner |
| `BLOCKED` | `overall.status` | Yes | At least one gate failed | Release manager + category owner |
| `PASS` | `overall.status` | No | All required gates satisfied | — |

If you are unsure whether a release is blocked, check `overall.status` first. If
it is `BLOCKED`, read `blockers` to find the failing category and its owner. If
it is `PASS` but a category is `WARN`, the release is not blocked — schedule
remediation for the missing optional evidence.
